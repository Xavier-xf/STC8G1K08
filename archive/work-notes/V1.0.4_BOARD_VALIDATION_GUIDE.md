# v1.0.4 板上验证指南

## 一、观察期验证（优先级最高）

### 目标
验证 v1.0.4 不会出现 v1.0.2 的误复位问题（407ms 后错误断言 AP_RESET）。

### 方法
烧录 v1.0.4 固件后，**保持正常运行至少 1 小时**，观察：

1. **V853 是否异常重启**
   - 检查 V853 系统日志：`dmesg -T | grep -i reboot`
   - 检查 uptime：`uptime`（应持续增长）

2. **P5.5 电压测量**（如果有条件）
   - 正常情况：~1.6-2.2V（高阻偏置）
   - 如果出现 <0.5V 的脉冲，说明误断言了 AP_RESET

3. **cpu_check_heartbeat 进程状态**
   - 确认进程正常运行：`ps | grep cpu_check`
   - 确认心跳持续发送：PH15 应该每 100ms 翻转（200ms 周期）

### 成功标准
- ✅ V853 持续运行 >1 小时无重启
- ✅ P5.5 始终保持高阻状态（无误脉冲）
- ✅ cpu_check_heartbeat 进程稳定运行

## 二、V853 ↔ STC 通信方案

### 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                         V853 (Linux)                         │
│                                                               │
│  ┌──────────────────────┐         ┌─────────────────────┐   │
│  │ cpu_check_heartbeat  │         │  cpu_check_ctl      │   │
│  │   (守护进程)          │         │   (控制工具)         │   │
│  │                      │         │                     │   │
│  │ - 每100ms翻转PH15     │         │ - 发送维护帧         │   │
│  │ - Unix socket服务器   │         │ - 直接操作GPIO       │   │
│  └──────────┬───────────┘         └──────────┬──────────┘   │
│             │                                │              │
│             └────────────┬───────────────────┘              │
│                          │ PH15 (GPIO)                       │
└──────────────────────────┼───────────────────────────────────┘
                           │
                           │ R78 (1kΩ)
                           │
┌──────────────────────────┼───────────────────────────────────┐
│                          │                                   │
│                      P5.4/INT2                               │
│                          │                                   │
│                  ┌───────▼────────┐                          │
│                  │  STC8G1K08     │                          │
│                  │                │                          │
│                  │ - 心跳监控      │                          │
│                  │ - P5.4 解码器   │                          │
│                  │ - 维护模式管理  │                          │
│                  │ - AP_RESET控制  │                          │
│                  └───────┬────────┘                          │
│                          │                                   │
│                      P5.5/AP_RESET                           │
│                          │                                   │
└──────────────────────────┼───────────────────────────────────┘
                           │
                           │ Q23
                           │
                      V853 复位电路
```

### P5.4 协议时序

STC 通过 P5.4 接收 V853 发来的维护命令，协议格式：

```
BREAK → SYNC → DELIMITER → PAYLOAD脉冲 → TRAILER

时序参数：
- BREAK:      ≥750ms    (长时间高电平)
- SYNC:       60-110ms  (短脉冲)
- DELIMITER:  240-360ms (中等脉冲)
- PAYLOAD:    60-110ms  (短脉冲，3个或4个)
- TRAILER:    ≥500ms    (结束后的静默)

命令：
- ENTER: 3个PAYLOAD脉冲 (进入或续约维护模式)
- EXIT:  4个PAYLOAD脉冲 (退出维护模式)
```

**正常心跳 vs 维护帧：**
- 正常心跳：200ms 周期的边沿，不满足 BREAK 条件，被解码器忽略
- 维护帧：以 BREAK 开始，明确区分

## 三、V853 端实现

### 1. cpu_check_heartbeat 守护进程

**功能：**
- 正常运行时持续发送心跳（每 100ms 翻转 PH15）
- 监听 Unix socket `/tmp/kocom_cpu_check.sock`
- 接收 `ENTER\n` 命令，发送完整的 ENTER 维护帧

**位置：** 
参考 `kocom-notification-blocker.md` 中的实现

**关键点：**
- 心跳和维护帧共用同一个 PH15 GPIO
- 发送维护帧时需要暂停心跳
- 使用互斥锁保护 GPIO 访问

### 2. cpu_check_ctl 控制工具

**功能：**
- `cpu_check_ctl enter`：连接 socket，发送 `ENTER\n`
- `cpu_check_ctl renew`：应用停止后，直接操作 GPIO 发送 ENTER 帧
- `cpu_check_ctl exit`：直接操作 GPIO 发送 EXIT 帧

**使用场景：**

#### a) 正常运行时进入维护模式
```bash
# 应用正常运行，cpu_check_heartbeat 在工作
cpu_check_ctl enter

# 返回 "SENT" 表示已发送 ENTER 帧
# STC 进入维护模式（默认租约 30 分钟）
# 此时 AP_RESET 保持高阻，不会复位 V853
```

#### b) 应用停止后续租
```bash
# 先停止应用和 cpu_check_heartbeat
systemctl stop kocom_app
systemctl stop cpu_check_heartbeat

# 续租（防止维护期间租约到期）
cpu_check_ctl renew

# 继续维护工作...
```

#### c) 退出维护模式
```bash
# 维护完成，恢复正常监控
cpu_check_ctl exit

# STC 立即退出维护模式
# 重新初始化复位控制器（30 秒启动宽限）
# 恢复 AP_RESET 监控功能

# 重启应用
systemctl start cpu_check_heartbeat
systemctl start kocom_app
```

### 3. 典型维护流程

```bash
# 步骤 1: 进入维护模式（应用运行时）
cpu_check_ctl enter
# 验证：V853 不会重启，即使心跳停止

# 步骤 2: 停止应用进行维护
systemctl stop kocom_app
systemctl stop cpu_check_heartbeat

# 步骤 3: 长时间维护时续租（可选，如果超过30分钟）
cpu_check_ctl renew

# 步骤 4: 完成维护，退出维护模式
cpu_check_ctl exit

# 步骤 5: 重启应用
systemctl start cpu_check_heartbeat
systemctl start kocom_app
```

## 四、STC 端行为

### 正常监控模式（默认）

```
INT2 边沿到达 → 更新心跳时间戳 → 解码器检查（忽略普通心跳）
     ↓
主循环检查心跳年龄
     ↓
超过 5 秒 → 断言 AP_RESET (200ms) → 释放 → 等待恢复
```

### 维护模式

```
收到 ENTER 帧 → 进入维护模式 → 设置租约（30分钟）
     ↓
主循环检测到维护模式
     ↓
强制 AP_RESET 高阻 → 跳过复位逻辑 → 仅喂 WDT
     ↓
持续监控租约 → 到期或收到 EXIT → 退出维护模式 → 恢复正常监控
```

### 维护模式的安全特性

1. **RAM-only 租约**：掉电或复位后自动恢复正常监控
2. **WDT 持续运行**：维护模式下也喂狗，防止 WDT 复位
3. **心跳继续记录**：INT2 边沿仍然更新心跳，只是不触发复位
4. **自动到期**：即使忘记 EXIT，30 分钟后自动恢复

## 六、故障排查

### 问题 1: cpu_check_ctl enter 无响应

**检查：**
```bash
# 确认 cpu_check_heartbeat 正在运行
ps | grep cpu_check_heartbeat

# 检查 socket 文件存在
ls -la /tmp/kocom_cpu_check.sock

# 查看进程日志
journalctl -u cpu_check_heartbeat -f
```

### 问题 2: 维护模式下 V853 仍然重启

**可能原因：**
1. ENTER 帧未正确发送（时序不对）
2. STC 未进入维护模式（解码失败）
3. 心跳停止时间过长，租约已到期

**排查：**
- 使用示波器观察 PH15 波形
- 确认 ENTER 帧时序符合规范
- 检查是否在 30 分钟内操作

### 问题 3: EXIT 后仍不触发复位

**可能原因：**
1. EXIT 帧未正确发送
2. STC 未正确退出维护模式

**排查：**
- 重新烧录固件
- 确认固件版本为 v1.0.4

## 八、注意事项

1. **UART 日志已关闭**
   - v1.0.4 无串口输出，只能通过 P5.5 电压和 V853 行为判断
   - 如需调试，可临时启用 `STC8G1K08_UART_LOG_ENABLE=1U`（但会 DATA 溢出）

2. **维护模式租约默认 30 分钟**
   - 长时间维护需要定期 `cpu_check_ctl renew`
   - 或修改 `MRT_DEFAULT_LEASE_MS` 重新编译

3. **WDT 持续运行**
   - 维护模式下 WDT 仍然生效（~2.1 秒超时）
   - 不会因为进入维护模式而禁用 WDT

4. **INT2 边沿优先级**
   - 心跳始终先于解码器处理
   - 即使在解析维护帧，心跳时间戳也会正确更新
